# Ground rules

This repository is the only channel between the planning session and the compute node.

## Who does what

| Role | Does | Where it writes |
| --- | --- | --- |
| **PI** (repository owner) | Decides. Approves experiment briefs. Stamps the compute node's work by merging its pull requests. | |
| **Planning session** | Literature review, paper plans, experiment briefs, analysis of returned results, paper drafts. Runs no experiments. | Directly on `main` |
| **Compute node** (Claude Code with GPU access) | Writes experiment code, runs experiments, returns results. | Its own branches only. Never on `main`. |

## Approval gates

1. **Before an experiment runs.** Its brief must be on `main` with `Status: approved`. The planning session sets that status only after the PI has explicitly approved the brief, and records the date. A brief marked `draft` must not be run.
2. **Before the node's work reaches `main`.** Code and results go on a branch and come back as a pull request. Only the PI merges it.
3. **Before a number enters a paper.** Its results pull request must be merged.

The node runs a brief as written. If a step cannot be done as written, it stops and reports that in the pull request. It does not improvise.

## Branch etiquette for the compute node

- One branch per brief, named `exp/<brief-id>` (for example `exp/P1-E01-few-shot`), created from the latest `main`.
- Pull `main` before starting each brief.
- Experiment code goes in `code/`, results in `results/<brief-id>/`, both on that branch.
- Commit small and often, and push the branch as you go.
- Open one pull request per brief, when the brief is done or when it is blocked.
- Never push to `main`, never merge your own pull request, never force-push.
- If a brief changes after approval, the planning session raises its revision number and the PI approves it again before the node continues.

## Flow

`paper plan` → `brief (draft)` → **PI approves** → `brief (approved)` on `main` → node works on `exp/<brief-id>` → pull request → **PI merges** → analysis → next brief

## Where things go

| Path | Contents | Written by |
| --- | --- | --- |
| `litreview/` | Reviews with their search logs, source index and evidence ledger | Planning session |
| `paper1/`, `paper2/` | Plan, outline, drafts and figures for each paper | Planning session |
| `briefs/` | One file per experiment, named `P<paper>-E<nn>-<short-name>.md` | Planning session |
| `code/` | Experiment code | Compute node |
| `results/<brief-id>/` | What the node returns for that brief | Compute node |

## What never goes in the repository

- Datasets and model weights. Record the source URL, version, checksum and licence instead.
- Tokens, passwords, keys or any other credential.
- Personal data.

## Commits and pull requests

- No AI co-author lines and no "generated by" lines, in commits or in pull requests.
- Never rewrite the history of `main`.

## Minimum contents of a results package

| File | Contents |
| --- | --- |
| `RESULTS.md` | What ran, headline numbers, deviations from the brief, anything that failed |
| `metrics/` | Raw per-run metrics as CSV or JSON: every seed, not only means |
| `config/` | Exact configuration files and command lines |
| `env.txt` | Commit hash of the code that ran, hardware, OS, package versions |
| `logs/` | Run logs |
| `figures/` | Each plot together with the script and data that produced it |
| `assets.md` | Datasets and weights used: source, version, checksum, licence |
